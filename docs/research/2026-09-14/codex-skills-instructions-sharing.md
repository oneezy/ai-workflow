# Sharing Codex skills and instructions across Windows and Ubuntu

Research dated September 14, 2026. This report follows Matt Pocock's installed `research` skill. It combines current primary documentation with the parent planning task's read-only inventory. It proposes no immediate system change. Only this report was added; installations, configuration, links, synchronization, personal memory, and existing project files were left unchanged.

## Recommendation

Recommend one Windows-native development workflow: repositories on a verified local Windows drive, Windows desktop Codex using its native agent, local Windows VS Code using Justin's existing `v2` profile, and a Windows-native Vite+/Node/package-manager toolchain with Windows Git. Use PowerShell for routine development. Keep the existing Ubuntu installation and its tools intact for optional Linux work. No repeated WSL workspace reopening or Git Bash workflow is required.

This recommendation follows Justin's latest priority of normal desktop/editor behavior and minimal maintenance. It deliberately trades away the earlier requirement that all coding-agent operations run in Ubuntu. Retaining a WSL terminal cannot meet both requirements automatically. If Linux execution for every agent operation remains mandatory, this recommendation is not acceptable; do not migrate repositories under that assumption. The WSL/SSH findings below remain evidence about alternatives, not the current recommended end state.

Maintain reusable skills and common instructions in one version-controlled source, then expose only selected content to each client. Project instructions remain with their project. Skill distribution and agent execution are separate decisions; neither a shared folder nor a WSL terminal selects the coding agent's host.

Justin's clarified requirement is automatic propagation of ordinary selected-skill additions, edits, and deletions made from either host, with an optional manual command or skill invocation. The smallest proposed design is one Windows-owned authoring collection accessible to both hosts, an automatic publisher retaining recoverable snapshots, and one managed collection link per client. Independent writable copies require a different synchronization design. Only conflicts, invalid packages, unavailable roots, or a changed trust boundary should interrupt normal operation. Neither design requires moving repositories or sharing Codex homes; neither has been implemented.

## Can Windows hold the canonical directory?

Yes, as a same-PC design based on supported mechanisms. Windows files at `C:/Users/Justin/...` are accessible in Ubuntu at `/mnt/c/Users/Justin/...`. The mount exposes the existing files; a Linux symlink placed in a Codex discovery directory can point to a selected skill within that mounted folder. No second copy or synchronization process is involved. [Microsoft filesystem interoperability](https://learn.microsoft.com/en-us/windows/wsl/filesystems), [Codex symlink discovery](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills).

For example, the proposed relationship is `/home/justin/.agents/skills/<selected-name>` pointing to `/mnt/c/Users/Justin/<canonical-folder>/skills/<selected-name>`. The canonical location is undecided. This is a path illustration, not an executed command. Linking a single selected skill avoids replacing the existing discovery directory or exposing every Windows skill. Merely opening the mounted source folder does not register its contents globally.

Put the Linux link in the Linux filesystem. Its creation uses Linux directory permissions; access to the Windows target still respects Windows permissions. It is different from creating a Windows link. Microsoft documents that WSL cannot grant more access to a mounted Windows file than the Windows user possesses. [WSL file permissions](https://learn.microsoft.com/en-us/windows/wsl/file-permissions).

The reverse arrangement, a Windows symbolic link pointing at `\\wsl.localhost\Ubuntu-26.04\...`, is possible at the Win32 mechanism level because symbolic links can target UNC paths. It adds dependency on WSL availability and target access. Windows link creation has privilege and API-specific conditions; this report did not test them or Codex's behavior through such a link. A junction is not a substitute for arbitrary UNC targeting. [Windows symbolic links](https://learn.microsoft.com/en-us/windows/win32/fileio/creating-symbolic-links), [creation API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createsymboliclinka), [junction constraints](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions).

For shared AGENTS content, prefer an explicit file export initially. The reviewed OpenAI page establishes its location and precedence, but does not specifically promise every cross-filesystem instruction-link arrangement. A later single-file link can be tested separately. Never redirect `CODEX_HOME` merely to share instructions.

Live links mean edits and deletions affect every linked reader immediately, including uncommitted edits. They provide neither version pinning nor per-client rollout. A pinned Git commit does not protect a dirty linked checkout. Validation before exposure requires a separate published snapshot, which a controller can update automatically without asking about each ordinary change. Missing targets, refresh behavior, and permission boundaries require acceptance checks. A link on this PC gives a Mac mini or VPS no access; those machines still need a deliberate delivery process.

Limit sharing to portable instructions and complete skill packages. Windows commands, drive paths, browser tooling, native binaries, executable permissions, case-sensitive filenames, and shell line endings may require host-specific resources. Identical bytes do not prove identical behavior. Microsoft recommends host-native filesystem placement for intensive development; that advice is not a benchmark showing this small documentation set will be slow. Keep Linux repositories where they are. [Microsoft filesystem guidance](https://learn.microsoft.com/en-us/windows/wsl/filesystems), [Git line-ending attributes](https://git-scm.com/docs/gitattributes).

## Controlled exports and dotfiles alternatives

A proposed canonical repository should contain selected skill trees, common instruction source, upstream repository URL and commit, license information, custom patches, and a manifest of intended destinations. It must exclude authentication, secrets, sessions, caches, generated memory, and whole Codex homes. OpenAI's Windows documentation describes whole-home sharing as an option, but Justin explicitly excludes that approach here. [Windows home-directory behavior](https://learn.chatgpt.com/docs/windows/windows-app).

For independent machines that only consume shared content, automatic one-way exports can deploy the chosen canonical revision into verified discovery paths. Review upstream source or trust changes separately; ordinary local edits need no recurring approval. Git fetch obtains objects and refs; it does not itself deploy files into Codex directories. [Git fetch](https://git-scm.com/docs/git-fetch). The proposed export contract should:

- Record the upstream commit and complete file hashes, including companion files. Keep intentional customizations separate from upstream updates.
- Compare the last deployed version, current destination, and proposed source. Stop on local edits or an unowned same-name path; never silently overwrite either.
- Log additions, changes, and deletions, with an optional preview mode. Automatically remove only previously managed files whose current hashes still match the previous deployment, after preserving the accepted version and verifying source availability.
- Preserve a rollback copy and deployment revision. Offline clients retain their last applied revision and report it honestly.
- Preserve consistent text line endings and required executable modes. Git can check symlinks out as ordinary link-text files when `core.symlinks=false`, so avoid assuming a cloned link is functional on Windows. [Git symlink behavior](https://git-scm.com/docs/git-config#Documentation/git-config.txt-coresymlinks).

Chezmoi can manage ordinary destination files, show a diff before applying, and template machine-specific differences. That could replace a custom exporter if the host matrix grows, but it adds another tool and policy to maintain. Its update/apply operations are explicit mutations; templates can also remove files, so exclusions and review matter. [Chezmoi daily operations](https://www.chezmoi.io/user-guide/daily-operations/), [machine differences](https://www.chezmoi.io/user-guide/manage-machine-to-machine-differences/). GNU Stow manages symlink arrangements; it does not remove the cross-OS target and permissions questions. [GNU Stow manual](https://www.gnu.org/software/stow/manual/stow.html). ## Automatic changes from either host

This section supersedes the earlier assumption that every export needs review. It is a proposed design, not permission to deploy a service. Share only a declared portable collection. A user, agent, or installer on either host can write it, but an installer must target that collection or a declared intake path. The collection boundary can authorize valid new packages automatically, without a prompt for each addition. This shared-source design requires selected writers to edit the authoring collection; arbitrary edits to independently installed copies require the two-copy design. An unrelated new directory under a host's other skill roots is not automatically selected for sharing. Host-specific skills, settings, hooks, secrets, and personal memory remain excluded.

### One collection versus two writable copies

One shared authoring directory gives both hosts the same files through their native path and `/mnt/c` path. It eliminates reconciliation between two content copies. Live links are simplest, but readers can see unfinished saves and deletion takes effect immediately. A single automatic publisher adds a useful boundary: detect a stable complete skill tree, validate structure and allowed paths, preserve the last accepted snapshot, and expose the new version automatically. This validation is not a guarantee that arbitrary instructions or scripts are trustworthy.

A collection link can also avoid creating a new link for every skill. The published Codex `0.154.0` source at commit `6b9826e3aa83b1a5947db50f4332cb9c65f1b340` uses recursive discovery for ordinary user/repo roots and follows directory symlinks. A Unix test discovers a nested skill through a linked collection. Therefore `~/.agents/skills/shared` pointing to a managed collection is supported by that loader's source, subject to scan limits. Actual Windows and alpha-extension behavior still needs acceptance testing. [Pinned loader](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/ext/skills/src/loader/host.rs), [collection-link test](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/ext/skills/src/loader/discovery_tests.rs). Individual links reflect existing target edits, but do not register a newly added sibling skill.

If both hosts instead need independent writable copies, the controller must distinguish changes since the last successful synchronization. Unison already documents comparison against prior archives, automatic recognition of equal changes, conflicting divergent edits, and temporary-file transfer before replacement. Evaluate such an existing engine rather than build a custom bidirectional synchronizer. Its exact Windows/WSL setup remains untested. [Unison manual](https://github.com/bcpierce00/unison/blob/master/doc/unison-manual.tex).

Syncthing provides watcher-plus-scan synchronization and preserved conflict copies, but its FAQ excludes synchronizing two folders in the same system. It is a later independent-machine candidate, not the default same-PC design. Its versioning is off by default and archives incoming changes, not its own local edits. [Syncthing behavior](https://docs.syncthing.net/users/syncing.html), [same-system limitation](https://docs.syncthing.net/users/faq.html#does-syncthing-support-syncing-between-folders-on-the-same-system), [versioning limits](https://docs.syncthing.net/users/versioning.html).

### What should trigger reconciliation?

For the Windows-owned source, propose one Windows-side coordinator, with a complete scan at startup and reconnection plus periodic reconciliation. If Ubuntu is unavailable, retain its last accepted state and pending work; do not keep WSL alive merely to poll it. Watchers only reduce delay. Node documents inconsistent watcher behavior across platforms and unreliable notifications on some virtualized or network filesystems; replacing a watched inode can also lose future events. Windows FileSystemWatcher can overflow its event buffer. Polling the small managed tree and comparing content hashes supplies recovery when events are absent, duplicated, or incomplete. [Node watcher caveats](https://nodejs.org/api/fs.html#caveats), [Microsoft FileSystemWatcher](https://learn.microsoft.com/en-us/dotnet/api/system.io.filesystemwatcher?view=net-10.0). Cross-WSL notification delivery was not measured here; do not make it a correctness requirement.

Codex documents `SessionStart`, `PostToolUse`, and `Stop` among its lifecycle hooks. They can request a reconciliation after Codex activity, but miss ordinary editor or installer writes outside that activity. User/project hook sources follow active configuration; changed non-managed definitions require trust review. The docs identify CLI `/hooks` controls, but do not establish identical availability in every installed desktop and IDE build. Plugin hooks cannot resolve the IDE plugin limitation. Background hook jobs are session-bound and cancelled at session end, so they are not a persistent watcher service. [OpenAI hooks](https://learn.chatgpt.com/docs/hooks). Keep any optional hook small and host-specific; do not depend on it for correctness.

A manual command and optional Codex skill should call the same coordinator's reconcile-once operation, using its lock and log. The skill is an on-demand entry point, not a daemon. Automatic schedules, interval, executable, and hook registration remain undecided and unconfigured. Normal operation should stay quiet; report actual conflicts, unavailable roots, invalid content, or required action.

### Failure and recovery contract

| Observed state | Proposed automatic response |
|---|---|
| Valid new or changed skill in the declared authoring collection | Wait for stable complete content, snapshot and publish automatically. |
| One-sided addition, edit, or deletion in a two-copy design | Propagate using the last synchronized baseline, only with both roots healthy. |
| Both copies changed to identical content | Record agreement without prompting. |
| Divergent same-path edits, delete-versus-edit, case collision, or unowned destination | Preserve both versions; pause the affected skill and report the conflict. |
| Missing mount, inaccessible root, wrong root identity, incomplete scan, or lost baseline | Keep last accepted content; retry. Never interpret this as deletion or recreate an empty source. |
| Confirmed deletion from a healthy managed source | Retain accepted content in recoverable history, record a deletion marker, then remove only the managed publication. |
| Reconnect after offline edits | Rescan before writing; compare revisions and resolve real conflicts rather than select by timestamp alone. |

Give each managed root an identity marker, a persisted last-accepted inventory, and recoverable history outside client discovery. Syncthing uses a missing folder marker to stop synchronization when a filesystem disappears; the same principle prevents an unavailable mount from becoming a mass deletion. [Syncthing missing-folder protection](https://docs.syncthing.net/users/faq.html).

Serialize coordinator runs and recheck source hashes before publishing. Stage a complete package and use a same-filesystem replacement strategy verified on each host; never assume an entire multi-file update is atomic. Treat rename as a managed move where identifiable, otherwise as recoverable add/delete after a quiet period. External editors do not obey the coordinator's lock automatically. No watcher can guarantee recovery of every short-lived unsampled version or prevent two arbitrary writers overwriting each other. Strict write serialization requires writers/installers to use a common operation or respect its lock. The minimum recoverability promise is the last accepted snapshot.

File convergence and client discovery are separate acceptance conditions. A collection link makes additions visible on the next successful scan, not necessarily inside an already-running task. Preserve active sessions; do not restart them automatically. Confirm fresh-task discovery and measure whether installed clients notice updates in place. Shared AGENTS edits likewise cannot rewrite guidance already loaded into an active run. Persistent hot reload across every client is not established by this research.

## Small reversible pilot for a later approval

Start with two new, uniquely named instruction-only skills and a short common AGENTS source in an isolated managed collection. Test automatic publication from a shared Windows authoring directory, accessed by either host, and a collection link where verified. Reserve independent writable-copy synchronization for a demonstrated requirement. No existing Matt skill needs reinstalling to prove the mechanism.

Accept only after ordinary additions, edits, renames, and recoverable deletions from each host propagate without approval prompts, including editor, agent, and installer-shaped writes. Fresh desktop tasks in the selected execution mode and any retained Ubuntu sidebar or CLI clients must identify matching full skill trees without new duplicates or load errors. Measure startup and discovery latency against the current baseline; retain automatically published host-native copies as a fallback if mounted discovery is too costly. Simulate missed events, controller restart, disconnected roots, partial writes, collisions, and concurrent edits; unavailable roots must cause zero deletions, and conflicts must preserve both versions. Verify manual and skill-triggered runs use the same state safely. Confirm rollback, project instructions, separate Codex homes, execution hosts, permissions, and authentication. Do not equate a successful read with permission to execute a helper script.

Choose the canonical location, shared-authoring versus independent-copy requirement, live versus validated publication, recovery retention, and acceptable discovery delay before implementation. Test actual client refresh and link behavior; none was exercised here. Plugin support in the IDE, future client versions, and other-machine delivery remain separate questions. This report resolves the practical options without selecting a memory backend or changing the current workflow.
