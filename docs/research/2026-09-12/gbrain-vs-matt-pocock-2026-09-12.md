**Gbrain and Matt Pocock's approach to agents**

Research observed September 12, 2026. This is a general capabilities assessment.

Gbrain and Matt Pocock's skills can complement each other. Matt's documented approach supplies a disciplined way to turn uncertainty into decisions, specifications, small implementation tasks, tests, and review. Gbrain supplies persistent memory and retrieval software, plus procedures for collecting and maintaining knowledge. Sharing an interest in reusable Markdown skills does not make them interchangeable products. [Ask Matt](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/ask-matt/SKILL.md), [gbrain architecture](https://github.com/garrytan/gbrain/blob/a6be012a3bcfac42e279630aedec5cda4a450e29/CLAUDE.md).

The strongest common idea is selective context. An agent should load relevant instructions and evidence when the task requires them. Matt's writing guidance adds precise completion conditions, pruning, progressive disclosure, and a distinction between the agent's context cost and the human's cost of choosing a workflow. "Fat skills" should mean useful procedure and judgment, not indiscriminately long files. [Writing for agents, publisher update August 24, 2026](https://www.aihero.dev/skills-writing-for-agents).

The linked essay is an older statement of philosophy. Its frontmatter says April 9, updated April 11, and draft-v4. Its last recorded file change is April 12. It proposes reusable procedures, conditional context routing, model judgment supported by code, and structured subject profiles. These are useful design principles. Its productivity multipliers, browser speed comparison, and event-feedback improvement are assertions in the essay, not measurements reproduced by this assessment. The July event narrative also appears in an April-dated draft. [Essay](https://github.com/garrytan/gbrain/blob/a6be012a3bcfac42e279630aedec5cda4a450e29/docs/ethos/THIN_HARNESS_FAT_SKILLS.md), [last file-changing commit](https://github.com/garrytan/gbrain/commit/baf3517868e5833ff8c1ff82d30d26877c1f1326).

Several distinctions matter when reading the comparison.

- A skill is an instruction that an agent follows. Its existence proves that a procedure is documented, not that the procedure always succeeds.
- A code path and regression test provide stronger evidence of an implemented mechanism. Reading them does not establish a passing runtime result.
- A maintainer's reported benchmark is attributed evidence. It is not an independent benchmark or a guarantee for another workload.

The differences become clearer at the task level.

| Concern | Matt's documented approach | Gbrain's contribution and limit |
|---|---|---|
| Choosing work | Ask Matt selects an engineering flow. Research informs decisions; large efforts can use Wayfinder before specifications and tickets. | Its resolver dispatches knowledge and personal-operation skills. It also overlaps on research and planning, so combining the systems requires a clear dispatch owner. |
| Building behavior | Behavior changes use TDD where appropriate, followed by review against both standards and specification. | The memory service can provide background evidence. Its resolver sends several engineering thinking tasks to optional GStack. |
| Recording meaning | Domain modeling keeps `CONTEXT.md` as a glossary, checks claims against code, and records consequential tradeoffs selectively in ADRs. | Entity pages, facts, timelines, and links hold broader knowledge about people, projects, and events. A remembered claim is not automatically an approved specification. |
| Continuing later | The phase guidance chooses among continuing, clearing, handing off, delegating, and compacting according to what the next phase needs. | Stored facts and context packs can supply selected information to a later session. They cannot recreate reasoning that was never captured. |
| Organizing knowledge | Context boundaries and document ownership keep each meaning near the work that owns it. | Gbrain separates databases, called brains, from content collections within a database, called sources. Cross-brain synthesis remains an agent decision. |

These rows describe documented procedures and the inference about how they could fit together. Gbrain's runtime has a deliberately small memory interface available over MCP. Its seven verbs are `recall`, `remember`, `entity`, `synthesize`, `forget`, `context_pack`, and `delta`. The last two support restoring selected context and obtaining changes since a cursor. Its protocol distinguishes contract conformance from retrieval quality. Conformance alone does not prove that the system found the best evidence. [Memory protocol](https://github.com/garrytan/gbrain/blob/a6be012a3bcfac42e279630aedec5cda4a450e29/docs/protocol/MEMORY_VERBS_v1.md).

Gbrain's broader [operation registry](https://github.com/garrytan/gbrain/blob/a6be012a3bcfac42e279630aedec5cda4a450e29/src/core/operations.ts) also registers graph, timeline, transcript, connector, and background-job operations. Their registrations were inspected, but connector authentication and scheduled workflows were not exercised. Its documented default preserves an existing agent's identity, makes automatic capture opt-in, and treats paid enrichment separately. [Operating defaults](https://github.com/garrytan/gbrain/blob/a6be012a3bcfac42e279630aedec5cda4a450e29/AGENTS.md).

Gbrain also has a much broader interface for administration and advanced operations. CLI and MCP share an operation contract. A remote CLI can forward calls through MCP, and a thin-client installation avoids silently querying an empty local database. Therefore, the project is not an example of avoiding MCP altogether. The useful lesson is to choose an appropriately small interface for the agent while keeping substantial execution logic behind it. [Architecture](https://github.com/garrytan/gbrain/blob/a6be012a3bcfac42e279630aedec5cda4a450e29/CLAUDE.md), [thin-client routing](https://github.com/garrytan/gbrain/blob/a6be012a3bcfac42e279630aedec5cda4a450e29/docs/architecture/thin-client.md).

Its resolver includes knowledge ingestion, briefing, recurring operations, research, and skill maintenance. It delegates several engineering thinking workflows to the separate GStack project when installed. Gbrain's memory functions work without that dependency. A comparison that credits gbrain with all of GStack would overstate the product inspected here. [Resolver](https://github.com/garrytan/gbrain/blob/a6be012a3bcfac42e279630aedec5cda4a450e29/skills/RESOLVER.md).

Skill improvement is a real difference in the sampled materials. Matt's [writing guidance](https://www.aihero.dev/skills-writing-for-agents) describes manual runs and diagnosis rather than an automated evaluation system. Gbrain adds a native optimizer and an [autobench procedure](https://github.com/garrytan/gbrain/blob/a6be012a3bcfac42e279630aedec5cda4a450e29/skills/skill-autobench/SKILL.md) that derives proposed evaluations from usage and corrections. Autobench explicitly makes human approval a workflow rule rather than a mechanically enforced gate. SkillOpt can apply accepted edits to user-owned skills automatically; its `--no-mutate` option produces proposals instead. Bundled-skill mutation has additional checks. The [SkillOpt guide](https://github.com/garrytan/gbrain/blob/a6be012a3bcfac42e279630aedec5cda4a450e29/docs/guides/skillopt.md) limits optimization to Markdown bodies and describes unfinished meta-edit work. This is benchmark-guided skill-text optimization, with different review requirements for different paths. It does not establish permanent improvement of every capability.

One substantive tradeoff concerns summaries. Gbrain's writing convention puts direct user statements first, then compiled understanding, then raw timeline material, then external enrichment. That is a documented writing convention, not proof of the runtime's ranking algorithm. It favors a useful maintained account of a subject. Matt's phase-boundary guidance emphasizes the loss of original reasoning when a session becomes a summary. Both concerns are valid. The practical combination is to preserve original evidence and provenance alongside the maintained account. [Gbrain quality convention](https://github.com/garrytan/gbrain/blob/a6be012a3bcfac42e279630aedec5cda4a450e29/skills/conventions/quality.md), [Matt's phase guidance](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/ask-matt/PHASE-BOUNDARIES.md).

Another tradeoff is operational burden. Gbrain's current authorization upgrade requires matching application and worker versions and review of legacy queued work. Some remote filesystem protections require platform support for `O_NOFOLLOW`. These are real service-maintenance concerns, beyond maintaining a directory of Markdown procedures. They do not apply equally to every deployment, but they make the essay's suggestion of permanent, maintenance-free capability too strong. [Upgrade guide](https://github.com/garrytan/gbrain/blob/a6be012a3bcfac42e279630aedec5cda4a450e29/docs/guides/authorization-upgrade.md).

Test coverage also needs precise language. The latest gbrain [commit message](https://github.com/garrytan/gbrain/commit/a6be012a3bcfac42e279630aedec5cda4a450e29) reports 29,333 passing tests and 232 E2E files. Those are maintainer-reported results. This assessment checked source and selected assertions, not CI logs or a running installation. Its [`test:full` script](https://github.com/garrytan/gbrain/blob/a6be012a3bcfac42e279630aedec5cda4a450e29/package.json) skips database E2E when `DATABASE_URL` is absent. The manifest requires Bun 1.3.11 or newer and declares macOS ARM64 and Linux x64 targets for `build:all`; this assessment does not establish native Windows compatibility.

Neither side eliminates instruction maintenance. Matt's August router repair demonstrates drift directly. Gbrain routes to detailed references, but its current `CLAUDE.md` still runs over 800 lines. The essay's roughly 200-line sketch is not a literal description of today's complete application or instruction set. [Matt's repair](https://github.com/mattpocock/skills/commit/8a475c438d90a2f1d7d3710c12658b60dc701a13), [gbrain instructions](https://github.com/garrytan/gbrain/blob/a6be012a3bcfac42e279630aedec5cda4a450e29/CLAUDE.md).

The useful combination is a workflow layer that decides how to work, with a memory layer that returns relevant evidence. Repository code, acceptance tests, and maintained decisions should retain their authority. Memory can point to them and supply dated background without becoming a competing specification. If both systems have a research router, choose which owns task dispatch; let the other supply context. This is a design recommendation derived from the comparison, not a claim that either project already implements that combination.

For a bounded engineering task, Matt's process and ordinary repository context may be sufficient. Gbrain becomes more relevant when the recurring problem is retrieving knowledge across sessions, archives, people, or projects. That benefit must justify database and integration upkeep. Nothing in this sample establishes that Matt rejects persistent memory, embeddings, or knowledge graphs.
